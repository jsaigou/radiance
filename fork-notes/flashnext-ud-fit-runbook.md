## 3. Fit model (the 89.0 GiB plan against Tohil's 120 GiB GTT)

Qwen3.6-35B-A3B calibration (measured, `docs/radiance-qwen36-w4w5-pilot-2026-11-14.md`):
21.01 GiB container, 262144 ctx, `--max-num-seqs 4`, `--kv-cache-dtype fp8`, MTP depth 2,
**36.3–36.4 GB measured resident** (GTT delta 32.3 GB, slot 32.2 GB). That calibration is used
only for the fixed non-weight overhead; the KV/state is computed from the config.

Flash-Next config (`config.json`, text_config): 48 layers, full attention every 4th (12 full,
36 linear), 1 MTP full-attention layer, `num_key_value_heads=2`, `head_dim=256`,
`num_attention_heads=24`, `linear_num_value_heads=48`, `linear_value_head_dim=128`,
`linear_key_head_dim=128`, `linear_conv_kernel_dim=4`, `num_experts_per_tok=10`,
`indexer_compress_ratio=4`, `indexer_budget=2048`, `max_position_embeddings=262144`.

At 262144 ctx, `--max-num-seqs 4`, fp8 KV, router `top_k=10` (model), MTP depth 2:

| component | formula | GiB |
|---|---|---:|
| full KV | 13 layers × 2 (K,V) × 2 kv-heads × 256 head-dim × 1 B × 262144 × 4 seqs | **13.0000** |
| GDN recurrent state | 36 layers × 48 v-heads × 128 × 128 × f32 4 B × 4 seqs | 0.4219 |
| GDN conv state | 36 × (2·16 + 48) × 128 × 4 (width) × bf16 2 B × 4 seqs | 0.0110 |
| QSA tail + block keys | 13 × 8 × 128 × bf16 × 4 seqs; 8 B/token × 262144 × 4 | 0.0079 |
| **KV/state total** | | **13.4408** |
| fixed overhead (calibration) | 36.3–36.4 GB measured − 21.01 GiB weights − 11.2496 GiB Qwen3.6 KV/state | **1.55–1.64** |
| **weights (the 89.0 plan)** | | **89.0029** |
| **total resident** | | **103.99–104.08** |

**Verdict: it fits.** 103.99–104.08 GiB = 111.66–111.76 GB against a 120.0 GiB
(128.85 GB) GTT pool: **~16.0 GiB headroom** (15.9 GiB if the calibration is the 36.4 GB
figure). The host has 123.4 GiB RAM; the token embedding can stay in host RAM (default
`--embedding-placement ram`), and the 26.8 GiB PLE n-gram table plus the vision tower are in
GTT under `--ngram-placement auto` if they fit (they do at 104 GiB total). If the n-gram table
is placed in RAM instead, GTT drops by 26.8 GiB and host RAM needs 26.8 GiB pinned; both fit.

**But the 89.0 GiB plan is not loadable as planned.** The fit above is a memory verdict, not a
load verdict. The exact mirror keeps the MTP layer (`blk.48`) bf16 (4.795 GiB); the arch
refuses a whole bf16 expert layer beside quantised trunk layers (512 protected experts, cap 8).
More importantly, every text layer mixes gate/up and down formats (e.g. IQ3_XXS gate/up +
IQ4_NL/Q5_0 down), and the current `MoeFP8` serves one encoding per layer except the rotated
w4/w5 codebook family (`family()` is `f==5||f==6||f==7`; the fast path's w3 adds a fourth).
See §5. The buildable variants are smaller and fit more easily:

| variant | weights | total resident | headroom |
|---|---:|---:|---:|
| exact mirror, MTP bf16 | 89.003 GiB | 103.99–104.08 GiB | 15.9–16.0 GiB |
| mirror with MTP layer at w4 (the fast recipe's rule) | 85.524 GiB | 100.51–100.60 GiB | 19.4–19.5 GiB |
| fast path (L5, `fn-fast`) | 85.637 GiB | 100.62–100.71 GiB | 19.3–19.4 GiB |

Levers, in the order to use if a load ever does not fit (all are reductions from the 104.0 GiB
exact-plan figure):

| lever | saving |
|---|---:|
| `--max-num-seqs 4 → 2` (the KV pool is `seqs × ctx`) | −6.50 GiB |
| `--max-model-len 262144 → 131072` | −6.50 GiB |
| MTP layer bf16 → w4nl64 (if the arch permits the layer) | −3.48 GiB |
| vision bf16 → fp8 (`v.*`) | −0.42 GiB |
| PLE n-gram table GTT → RAM (`--ngram-placement ram`) | −26.82 GiB GTT, +26.82 GiB host |
| `--kv-cache-dtype fp8 → fp8_v4` (supported at head_dim 256, gqa 12) | −2.84 GiB KV |
| `--kv-cache-dtype fp8 → k6_v4` | −4.06 GiB KV |

Disk and conversion: the container is 95.57 GB (89.00 GiB); the bf16 source is ~351.6 GB; the
UD GGUF shards and the 580 MB imatrix are additional reads. `/` and `/home` have 5.4 TB free,
so the write is not a risk; the page cache is. Conversion is CPU-only (no GPU lock needed).
Qwen3.6 measured 21.01 GiB RTN in 1828 s and GPTQ in 3427 s with 16 threads; scaling by 4.2×
gives **~2.2 h RTN and ~4.0 h GPTQ**, and the IQ2_S/IQ3_XXS grid encoders are the slow path, so
plan on **3–6 h RTN, 6–10 h GPTQ**. `ud_map build` runs the `--plan-only` pass first, which
fails fast on a missing format; do not start the long conversion before that passes.

## 4. Runbook for the lead (after the merges)

Set the tree and build once the branches are merged (never `/opt/radiance`):

```sh
SRC=~/radiance-test/src-full          # or a fresh merged worktree
BUILD=$SRC/build
MODEL=/opt/tohil/models/Qwen3.8-Flash-Next-UD-MIRROR
mkdir -p "$MODEL"
```

### 4.1 Preconditions

- [ ] Merge L3 (`kernel-dense-wire`, `13ab816`), L2 (`kernel-iq4xs`, `ead15cc`) and L1
      (`kernel-iq3xxs`, `acdc63f`) and rebuild (`cmake --build "$BUILD" -j`); the tree must be
      after the merge, not the current base `2a3200f`.
- [ ] Add the IQ4_XS routed-expert GEMM (6 layers, 4.98 GiB) — **not in L1/L2/L3**.
- [ ] Extend `MoeFP8` to serve per-projection unrotated formats in one layer (the UD map mixes
      gate/up and down in all 48 layers; `family()` currently only admits the rotated w4/w5
      forms, plus the fast path's w3).
- [ ] Decide the MTP layer: either teach the arch to serve the kept bf16 layer, or write
      `blk.48` at w4nl64 (the fast recipe's rule; −3.48 GiB, measured no acceptance difference
      on Qwen3.6).
- [ ] Re-run the §2 `--plan-only` preflight; it must reach the end without a dtype refusal.

If the lead wants the earliest container, the **fast path** (`--policy fast`, 85.637 GiB) needs
only L3 plus the `w3nl64a8h` arch declaration in `tools/ud_map/RESULTS.md`
("For the lead: the one arch change this lane needs"); it avoids the IQ4_XS expert and the
mixed-family problem.

## 5. Blockers and known risks

1. **IQ4_XS routed experts have no kernel (4.98 GiB, 6 layers: 15–18, 32, 47).** L2 only adds
   the `token_embd` gather (`ead15cc`). The five-way map `IQ4_XS` for gate/up is not served by
   `format_of` (its scale is 6-bit/256, not the IQ4_NL f16/32 form). Without a kernel those
   layers cannot be built; the fast path maps IQ4_XS to `w4nl64a8h` and avoids it.
2. **One encoding per layer.** The current `MoeFP8::declare` sets `fmt[0]=fmt[1]=want` from the
   probed gate/up expert and only rescans per-projection for the rotated family
   (`family(f) = f==5||f==6||f==7`). The UD map mixes gate/up and down in **all 48 layers**
   (IQ3_XXS/IQ2_S/IQ4_XS gate/up with IQ4_NL/Q5_0/Q2_0 down), so the mirror container stops at
   layer 0's down projection (`Q5_0` vs the layer's IQ2_S) even after L1/L2/L3. This is an arch
   change (per-projection format flags, `edt_of`, `ecodes`, `unrot`, kernel dtype), not a recipe
   change.
3. **The kept bf16 MTP layer is refused.** `blk.48` (source `mtp.layers.0.*`) is 512 bf16
   experts; `MoeFP8` keeps at most 8 protected experts, so the exact 89.0 GiB plan does not
   load. Options: MTP at w4nl64 (−3.48 GiB; measured no acceptance difference on Qwen3.6) or
   arch support for a bf16 MTP expert layer.
4. **Build predates L1/L2/L3.** The current `rad-convert --plan-only` refuses at
   `blk.0.ffn_gate_up_exps.0.weight` (IQ2_S). Rerun the §4.2 preflight after each merge; the
   named tensor is the next blocker. Do not work around it by editing the mirror recipe.
5. **Time/disk.** CPU-only conversion, 3–6 h RTN (6–10 h GPTQ); 95.57 GB output plus the
   351.6 GB source and page-cache churn. 5.4 TB free, but do not run two conversions at once.
6. **Memory.** 104.0 GiB at 262144×4 leaves ~16 GiB of GTT; the GTT counter blind spot means
   use `InferenceRSSBytes`, and verify `n_ctx` via `/props` after every switch. If a future
   build is larger, use the §3 levers in order.
7. **Quality reference.** No FP8 Flash-Next `.rad` on Tohil and no 176 GB headroom to make one;
   KL is only possible with a reference from a larger host. Task-level comparison against the
   UD GGUF on llama.cpp is the fallback.
